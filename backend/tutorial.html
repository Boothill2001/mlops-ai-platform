CICAAD MLOps AI Platform

A deep, file-by-file tour of the backend: a supplier-risk inference API with caching, a permission-aware RAG pipeline, batch scoring, drift detection, and a golden-set evaluation harness — built with FastAPI, scikit-learn, NumPy, and SQLite. Each section explains why the file exists, what its key functions do, what can go wrong, how the design would change at scale, and how to talk about it in a senior MLOps interview.

Architecture Overview

The platform is a single FastAPI application (app/main.py) exposing six routers under /api/v1: inference, RAG, batch, evaluation, monitoring — and this tutorial. Every request passes through a middleware that injects a 12-hex-char request ID into a ContextVar so log lines and responses (X-Request-ID header) are correlated. The app lifespan hook calls init_db() and seed_all() so the SQLite schema and demo documents exist before the first request.

The three request flows

  • Real-time inference — POST /api/v1/inference/supplier-risk: cache lookup → feature engineering → production model from the registry → prediction + explanation → write-through cache → history log. Every response carries latency_ms, cache_hit, and model_version.
  • RAG query — role validation → cache → embed query → permission pre-filtered cosine search (over-fetch top_k * 2) → hybrid rerank → extractive answer with citations.
  • Operational plane — batch CSV scoring in a background thread with per-record retry; monitoring computes latency percentiles, error rate, cost estimates, and drift from the same request_history table every service writes into; evaluation replays a golden question set through the live RAG pipeline.
Why this layering

Routes are thin (validate → delegate), services own business logic, repositories own SQL, and the ML layer is behind an abstract interface. Each layer is swappable: SQLite → Postgres, in-memory vectors → pgvector, rule-based model → trained model — without touching the API surface. That separation is the whole point of the exercise: the architecture is production-shaped even where individual components are deliberately simple.

Key Design Decisions

1. Pre-filtering RAG security (permission filter before ranking)

Document-level permissions are enforced before similarity ranking: VectorStore.search() accepts a filter_fn and skips unauthorized documents before computing cosine similarity. The naive alternative — retrieve top-k, then drop forbidden results — has two failure modes: (a) a user may receive fewer than k results, and the count delta leaks the existence of restricted documents; (b) worse, a rerank or answer-generation step downstream may have already seen restricted text. Pre-filtering makes unauthorized documents invisible to the entire pipeline. The docstring in permission_service.get_permission_filter() states this explicitly — it is a deliberate security invariant, not an implementation accident.

2. Rule-based model with trained-model fallback path

RuleBasedModel is a transparent weighted linear scorer that ships on day one and is perfectly explainable. TrainedModel wraps a pickled sklearn classifier but holds a RuleBasedModel as fallback: if the artifact is missing or fails to load, predictions degrade gracefully instead of 500ing. The registry serves whichever version is staged "production". This encodes a real MLOps principle: the serving contract is stable; the model behind it is an implementation detail with a safety net.

3. Composite cache keys (namespace + sorted params + SHA-256)

CacheService._make_key() builds sha256(json.dumps({"ns": namespace, **sorted(params)})). Sorting the params dict makes the key order-insensitive — the same logical request always maps to the same key regardless of field order. The namespace prevents cross-feature collisions ("inference" vs "rag"), and hashing yields fixed-length keys safe for any backing store. RAG cache keys include the role, so a viewer can never be served an answer computed for an admin — the cache respects the permission boundary.

4. JSD drift detection on intent distributions

DriftService classifies recent traffic into intents (risk_assessment, compliance, pricing, quality, general) and compares that distribution against a frozen baseline using Jensen–Shannon divergence. JSD was chosen over raw KL divergence because it is symmetric and bounded (0 → ln 2), which makes fixed thresholds (warning=0.20, alert=0.35) meaningful; KL is unbounded and blows up on zero-probability bins. This is input/usage drift — the earliest, cheapest signal that the world your model sees no longer matches the world it was tuned for.

5. Mock embeddings via HashingVectorizer behind a Protocol

EmbeddingService programs against an EmbeddingBackend Protocol with two implementations: MockEmbedding (sklearn HashingVectorizer, 256-dim, L2-normalized — deterministic, zero model download, instant tests) and SentenceTransformerEmbedding (all-MiniLM-L6-v2, lazily imported). A config flag (embedding_provider) swaps them. The hashing trick gives real lexical-overlap similarity that exercises the entire retrieval pipeline honestly, while keeping CI hermetic.

Interview framing for the whole system

"I built the platform contract-first: every architectural seam — model, embeddings, cache, storage — is an interface with a cheap local implementation and a documented production swap. That let me demonstrate the operational parts of MLOps (caching, drift, evaluation, observability, permission-aware retrieval) end-to-end without cloud dependencies, and each mock names its real replacement: Redis, pgvector, sentence-transformers, MLflow."

Service

services/inference_service.py — Real-time prediction orchestrator

Purpose

The single entry point for real-time supplier-risk predictions. It owns the orchestration — cache → features → model → explanation → cache write → history log — but none of the ML math, feature logic, or storage details. Routes call it; it calls everything else.

Key functions

MemberWhat it does
InferenceService.predict(request) Starts a trace (request ID + timer). Checks the cache using the full request payload as the key. On hit: returns cached body with cache_hit=True and a fresh request_id/latency. On miss: builds features, fetches the production ModelVersion from the registry (raises RuntimeError if none), calls predict() and explain(), assembles a SupplierRiskResponse, writes through to cache, and logs to history.
get_inference_service() Module-level lazy singleton wiring CacheService, HistoryService, and a ModelRegistry. Constructor injection keeps the class unit-testable with fakes.
# The core orchestration, condensed:
cached = self._cache.get("inference", **request.model_dump())
if cached: return SupplierRiskResponse(**cached, cache_hit=True, ...)

features = build_features(request.model_dump())
model_version = self._registry.get_production()   # RuntimeError if None
prediction = model_version.model_instance.predict(features)
explanation = model_version.model_instance.explain(features)
# ... respond, cache.set(...), history.log_request(...)
Why it exists

Without an orchestrator, cache logic and model dispatch leak into route handlers and get copy-pasted into the batch path. Centralizing means one place defines the serving contract: every prediction is cached, versioned, explained, and logged. Note that cached responses still get a fresh request_id and real measured latency — observability metadata is never cached, only the model output is.

What can go wrong
  • Cache hits are not logged to history. log_request() is only called on the miss path, so cache_hit_rate computed from history undercounts hits. Debugging tip: if monitoring shows a near-zero hit rate but responses return cache_hit=true, this is why.
  • Stale predictions after model promotion. The cache key does not include the model version; promoting a new model keeps serving old cached scores until TTL (300 s) expires. Fix: add model_version to the cache params or invalidate the namespace on promotion.
  • Singleton state in tests. The module-level _instance persists across tests; reset it (or inject fresh dependencies) in fixtures or tests will share cache state.
  • No production model → 500. RuntimeError("No production model registered") surfaces as an unhandled 500. Reasonable fail-fast for a demo; production would map it to a 503 with an alert.
Production tradeoffs
  • predict() is async but every call inside is synchronous (SQLite, sklearn). Fine at demo scale; at real scale, blocking calls move to a thread pool (run_in_executor) or the model moves behind a dedicated serving layer (Triton, Ray Serve, KServe).
  • History logging is a synchronous DB write on the request path. At scale it becomes fire-and-forget: a queue/async writer, or events emitted to Kafka and aggregated downstream.
  • Shadow/canary evaluation would hook here: score with both production and canary models, serve production, log both.
Interview talking points
  • "Cache-aside with write-through: read the cache first, compute on miss, populate on the way out. The key is the full request payload, so any input change is automatically a different key."
  • "Every response carries model_version — that's prediction lineage. When a customer disputes a score, I can tell exactly which model produced it."
  • Point out the stale-after-promotion caveat yourself — knowing your own cache-invalidation gap is a stronger signal than pretending the design is perfect.

services/cache_service.py — Two-tier LRU + SQLite cache

Purpose

A namespaced key-value cache with two tiers: an in-process OrderedDict LRU (fast path, bounded at cache_max_size=1000) backed by a SQLite cache_entries table (survives restarts, enforces TTL). It mimics the local-cache-in-front-of-Redis pattern you would deploy in production.

Key functions

MemberWhat it does
_make_key(namespace, **params) Canonical key: JSON of {"ns": ns, **sorted(params)} → SHA-256 hex. Sorted params make the key order-insensitive; default=str tolerates non-JSON types; the namespace isolates features.
get(namespace, **params) Memory first (move_to_end marks recency). On memory miss, reads SQLite; a hit is promoted into memory (read-through) and eviction runs.
set(namespace, value, **params) Writes both tiers: memory (then LRU evict) and SQLite with TTL — write-through, so a restart repopulates from disk.
invalidate(...) / _evict() Removes one key from both tiers / pops the least-recently-used entries (popitem(last=False)) while over capacity.
Why two tiers

Memory gives microsecond hits with zero I/O; SQLite gives durability and TTL. The promotion-on-read pattern means hot keys migrate to the fast tier automatically. It is the exact shape of "process-local cache + shared Redis" — only the second tier's technology changes in production.

What can go wrong
  • The memory tier ignores TTL. Only CacheRepository.get() checks expiry. An entry that stays hot in memory can outlive its TTL indefinitely. Debugging tip: if you see stale data past TTL, check whether the key ever left the memory tier.
  • Mutable value aliasing. get() returns the dict stored in memory by reference — a caller that mutates it corrupts the cache. (This is why RagService caches response.copy() and why the cached RAG dict gets mutated fields patched on each hit — the copy on write protects the shared entry.)
  • Multi-process incoherence. Two uvicorn workers each have their own memory tier; an invalidate() in worker A leaves a stale entry in worker B until its LRU evicts it.
  • Theoretical hash collisions are a non-issue with SHA-256, but forgetting the namespace when calling get/set silently reads the wrong keyspace — always grep for the namespace constant when debugging misses.
Production tradeoffs
  • Swap SQLite tier for Redis: native TTL (SETEX), atomic ops, shared across replicas, pub/sub for invalidation broadcasts to local tiers.
  • Add metrics: hit/miss counters per namespace, eviction rate, memory-tier vs persistent-tier hit split.
  • Consider stampede protection (single-flight locking or probabilistic early expiry) so a hot key expiring doesn't trigger a thundering herd of model calls.
Interview talking points
  • "Cache key design is the interesting part: namespace prevents cross-feature collisions, sorted params make keys canonical, and hashing bounds key size. For RAG I put the user's role in the key so caching can never bypass authorization."
  • "OrderedDict with move_to_end is the textbook O(1) LRU — same data structure functools.lru_cache uses internally."
  • Be ready for: "What's your invalidation story when the model updates?" — answer: version the namespace or include model_version in the key.
Service

services/history_service.py — Request audit log

Purpose

A thin service over HistoryRepository that records every served request (request ID, endpoint, latency, status, cache_hit, model version, payload) and answers aggregate questions. It is the platform's system of record: monitoring, drift detection, and debugging all read from the rows this service writes.

Key functions

MemberWhat it does
log_request(...) Inserts one row into request_history. The payload dict is stored as JSON so drift analysis can later re-classify queries without a schema migration.
get_history(endpoint, limit) Recent rows, optionally filtered by endpoint, newest first.
get_stats(endpoint) Pulls up to 10,000 rows and computes total count, mean latency, and cache-hit rate in Python.
Why it exists

Prediction logging is the foundation of every downstream MLOps capability: latency SLO tracking, drift detection, incident forensics ("what did we return for request X?"), and eventually retraining data. Making it a service (not inline SQL in each caller) means one schema and one write path.

What can go wrong
  • Aggregation in Python, not SQL. get_stats loads 10k rows to compute an average that SQLite could do with AVG(). Fine now; a memory/latency trap once the table grows. The 10k cap also silently truncates stats on busy systems.
  • Status string mismatch: inference logs status="ok" while monitoring counts errors as status != "success" — so every request counts as an error in the error-rate metric. Classic cross-service constant drift; a shared enum fixes it.
  • Payloads may contain sensitive data. Anything in the request lands in the DB as plaintext JSON; production needs field-level redaction and a retention policy.
  • Synchronous write on the hot path — a locked or slow DB adds directly to user latency.
Production tradeoffs
  • High-volume systems make this asynchronous: emit an event to Kafka/Kinesis, aggregate into a warehouse (BigQuery/ClickHouse), keep only recent hot data in an OLTP store.
  • Metrics that monitoring reads every few seconds should come from a metrics pipeline (Prometheus counters/histograms), not from re-scanning an audit table.
  • Add partitioning/TTL on the table — audit logs grow monotonically forever otherwise.
Interview talking points
  • "Every prediction is auditable: request ID, model version, inputs, latency. That's the difference between an ML demo and an ML system — you can answer 'why did the model say that, and which model was it?'"
  • "I'd separate the two workloads this table currently serves: audit (append-only, long retention) and metrics (pre-aggregated, short retention). Coupling them is the current design's main debt."

services/embedding_service.py — Pluggable text embeddings

Purpose

Turns text into L2-normalized vectors for similarity search, behind a swappable backend. It also owns the lazy, thread-safe bootstrap of the vector store: the first embed call embeds all seeded documents exactly once (double-checked locking) so the store is queryable without an explicit indexing step.

Key pieces

MemberWhat it does
EmbeddingBackend (Protocol) Structural interface: embed(text) → ndarray, embed_batch(texts) → ndarray. No inheritance required — duck typing checked statically.
MockEmbedding HashingVectorizer(n_features=256, norm="l2", alternate_sign=False). Deterministic, stateless (no vocabulary to fit), no model download. Re-normalizes defensively against zero vectors.
SentenceTransformerEmbedding all-MiniLM-L6-v2 with normalize_embeddings=True. Import is inside __init__ so the dependency is optional; a clear ImportError message tells you how to install it.
EmbeddingService._ensure_store_embeddings() Double-checked lock: if the store has documents but no embeddings yet, batch-embed all chunk texts and attach the matrix. Runs at most once per process.
get_embedding_service() Thread-safe singleton (lock-guarded), unlike the simpler singletons elsewhere — embeddings can be hit concurrently by RAG and evaluation.
Why HashingVectorizer for the mock

Random vectors would make retrieval tests meaningless; a real transformer makes CI slow and network-dependent. The hashing trick is the middle path: token counts are hashed into a fixed 256-dim space, so texts that share words genuinely land near each other under cosine similarity. The whole pipeline — search, permission filter, rerank, evaluation metrics — is exercised with real signal, deterministically, in milliseconds.

What can go wrong
  • Backend switch invalidates every stored vector. Mock (256-dim, lexical) and MiniLM (384-dim, semantic) are incompatible spaces; flipping embedding_provider without re-embedding the store gives shape errors or garbage similarities. Rule: embedding model version is part of the index schema.
  • Hash collisions: at 256 features, unrelated tokens share buckets. Harmless for a demo, but explains occasional odd retrievals; raise n_features if it bites.
  • No synonym understanding: the mock is purely lexical — "cost" will not match "pricing". Golden-set evaluation numbers must be interpreted with that in mind.
  • Bootstrap ordering: _ensure_store_embeddings only runs from embed(). Documents added later via add_documents() without embeddings will never be indexed, because _initialized is already true.
Production tradeoffs
  • Real deployments use a hosted embedding API or a GPU-served model, with batching, retry/backoff, and an embedding cache (embeddings are pure functions of text — perfect cache candidates).
  • Index migrations become a first-class operation: blue/green indexes, re-embed offline, cut over atomically.
  • Track embedding latency and dimensionality as config, not constants.
Interview talking points
  • "I used a Protocol instead of an ABC — structural typing means any object with embed/embed_batch satisfies the interface, which keeps test doubles trivial."
  • "The mock isn't random — HashingVectorizer gives deterministic lexical similarity, so retrieval tests assert real behavior. And the design forces the right production question: what happens to your index when the embedding model changes?"
  • "Double-checked locking on both the singleton and the store bootstrap — the naive lazy singleton has a race under concurrent first requests."

services/permission_service.py — Role-based document access

Purpose

Pure, stateless authorization logic for the RAG pipeline. Defines a four-level role hierarchy (admin=4 > manager=3 > analyst=2 > viewer=1) and produces the filter closure that VectorStore.search() applies before ranking.

Key functions

FunctionWhat it does
can_access(user_role, doc_metadata) True if the role is explicitly listed in the doc's allowed_roles, or if the user's numeric level ≥ the minimum level among allowed roles (hierarchical override: a manager can read anything an analyst can).
get_permission_filter(user_id, user_role) Returns a Callable[[dict], bool] closure over the role, passed as filter_fn into vector search. Its docstring documents the pre-retrieval security invariant.
get_accessible_doc_count(role, documents) Counts accessible docs — used by RagService to report permission_filtered_count transparently in responses.
Why pre-retrieval filtering (the security invariant)

Filtering after ranking leaks information two ways: result-count changes reveal that hidden documents exist, and restricted text may reach the reranker or answer generator before being dropped. Applying the filter before similarity computation means unauthorized content never enters the pipeline at all. This is the RAG-era version of row-level security — and it's the single most common security bug in production RAG systems.

What can go wrong
  • Missing metadata fails open-ish: a doc with no allowed_roles yields min(default=0), so every known role (level ≥ 1) can access it. For sensitive corpora you'd want fail-closed: no metadata → no access.
  • Unknown roles map to level 0 and are denied by the hierarchy — but note RagService already rejects unknown roles before this layer runs (defense in depth).
  • user_id is accepted but unused — the API is shaped for per-user ACLs/tenancy but only role is enforced today. Don't claim user-level isolation in a review.
  • Linear-scan cost: the closure runs per document per query. Invisible at demo size; a real vector DB needs this as an indexed metadata pre-filter, not a Python callback.
Production tradeoffs
  • Real vector DBs (pgvector WHERE clauses, Qdrant/Pinecone metadata filters, OpenSearch DLS) push the filter into the index so filtering stays sublinear.
  • Roles would come from a JWT/OIDC claim validated by middleware, not a request body field — the current design trusts the caller's self-declared role.
  • Add audit logging of denied accesses, and per-tenant namespaces for multi-tenancy.
Interview talking points
  • "Pre-retrieval permission filtering is my go-to RAG security answer: post-filtering leaks document existence through result counts and lets restricted text reach downstream components."
  • "The service is pure functions over dicts — no I/O, no state — so the security-critical logic is trivially unit-testable, which is exactly where you want your test density."
  • "I also surface permission_filtered_count in responses — users can see that results were withheld without seeing what, which builds trust in the system."

services/retrieval_service.py — Secure semantic retrieval

Purpose

A small but deliberate composition point: it is the only code path that touches the vector store for queries, and it guarantees that every search is (1) embedded with the configured backend and (2) wrapped in the caller's permission filter. Security by construction — you cannot reach the store without going through the filter.

Key function

def retrieve(self, query, user_id, user_role, top_k=5):
    query_embedding = get_embedding_service().embed(query)          # also lazily indexes the store
    permission_filter = get_permission_filter(user_id, user_role)   # closure over role
    return get_vector_store().search(
        query_embedding=query_embedding, top_k=top_k, filter_fn=permission_filter)
Why a dedicated layer for 15 lines

If RagService called the store directly, the permission filter would be an optional argument someone could forget. Funneling all retrieval through one method makes the secure path the only path — the same reason you wrap raw SQL behind repositories. It's also the seam for future retrieval upgrades (hybrid BM25+vector, multi-query expansion, HyDE) without touching RAG orchestration.

What can go wrong
  • Empty results are ambiguous: "no similar docs", "all docs filtered by permissions", and "store not yet indexed" all return []. When debugging empty RAG answers, check store.embeddings is not None first, then the role's accessible-doc count.
  • No score threshold: top-k always returns k results if any candidates exist, even at cosine similarity ≈ 0. Downstream grounding quality depends on the reranker demoting junk; production should apply a minimum-similarity cutoff.
  • Service-locator wiring (get_*() calls inside the method) is convenient but hides dependencies — tests must patch module-level singletons rather than inject fakes.
Production tradeoffs
  • Hybrid retrieval (dense + BM25 with reciprocal-rank fusion) typically beats either alone on enterprise corpora — this class is where it would land.
  • Add retrieval telemetry: per-query candidate counts, similarity score distributions, filter rejection counts. Silent retrieval degradation is the most common cause of "the RAG got worse".
Interview talking points
  • "Retrieval is a single choke point that makes permission filtering non-optional — security by construction rather than by convention."
  • "I over-fetch at the caller (2×top_k) so the reranker has candidates to work with — retrieval recall and final precision are separate dials."

services/rerank_service.py — Hybrid second-stage ranking

Purpose

The second stage of a two-stage retrieval funnel. First-stage vector search optimizes recall (fetch 2×top_k candidates cheaply); the reranker optimizes precision by blending the vector score with exact keyword overlap: combined = 0.6 · vector_score + 0.4 · keyword_score, where keyword_score is the fraction of query words present in the chunk.

Key function

MemberWhat it does
rerank(query, chunks, top_k) Tokenizes query and each chunk into lowercase word sets, computes overlap ratio |Q ∩ C| / |Q|, blends with the original score 60/40, sorts descending, truncates to top_k. Guards the divide-by-zero on empty queries.
Why hybrid scoring

Dense embeddings can rank a vaguely-related chunk above one containing the user's exact term (especially with small embedding models); pure keyword matching misses paraphrases. Blending recovers exact-term precision while keeping semantic recall — a stand-in for the cross-encoder rerankers used in production, with the identical interface (query + candidates in, re-scored top_k out).

What can go wrong
  • Naive tokenization: split() keeps punctuation ("pricing?" ≠ "pricing"), no stemming, and stop-words ("the", "is") count as matches — inflating keyword scores for chunks that share only filler words. Debugging tip: print both score components when a bad chunk wins.
  • Score scale mixing: the blend assumes both components live in [0,1]. Cosine scores from the normalized mock embeddings do, but a different first-stage scorer (e.g. inner product, BM25) would silently skew the 60/40 balance.
  • Hardcoded weights: 0.6/0.4 was picked by intuition, not tuned. The evaluation service is exactly the harness you'd use to tune it — mention that pairing.
Production tradeoffs
  • Replace with a cross-encoder (e.g. ms-marco-MiniLM) or a hosted reranker (Cohere Rerank). Cross-encoders attend over (query, chunk) jointly — much more accurate, ~10–50 ms per candidate, which is precisely why you only run them on a small candidate set from stage one.
  • The funnel shape is the durable idea: cheap-and-broad, then expensive-and-narrow. Same pattern as recommender candidate-generation → ranking.
Interview talking points
  • "Two-stage retrieval: bi-encoder for recall, reranker for precision. My reranker is a keyword-overlap hybrid, but the interface is exactly where a cross-encoder drops in."
  • "Retrieval quality changes should be gated by the golden-set evaluation — rerank weights are a tunable, and recall@k / citation accuracy are the objective."

services/rag_service.py — RAG pipeline orchestrator

Purpose

Orchestrates the full question-answering flow: role validation → cache → retrieval (over-fetched) → rerank → answer synthesis → citations → cache write → history log. Also computes transparency metadata: permission_filtered_count (how many docs the caller could not see) and grounded (whether the answer is backed by retrieved text).

Key functions

MemberWhat it does
query(user_id, role, query_text, top_k) Rejects unknown roles up front (uniform "Access denied" body, no exception). Checks cache keyed on (role, query). On miss: retrieves top_k * 2 candidates through the permission-aware retriever, computes filtered-count transparency stats, short-circuits with a graceful grounded=False body when nothing is retrievable, else reranks to top_k, generates the answer, builds citations with rounded relevance scores, caches a copy of the response, and logs history.
_generate_answer(query, chunks) Mock extractive generator: takes the first sentence of the top 3 chunks, attributes each with [Source: title], and appends a grounding note. If llm_provider != "mock" it returns a placeholder — the seam where a real LLM call goes.
_get_cache_service_safe() / _get_history_service_safe() Late, exception-swallowing imports: cache and history are treated as optional dependencies. If either fails to initialize, RAG still answers — graceful degradation of non-critical paths.
Why this shape
  • Role in the cache key: answers are computed against a role-filtered corpus, so they are only valid for that role. Caching on query alone would leak an admin's answer to a viewer.
  • Over-fetch then rerank: stage one optimizes recall, stage two precision (see rerank section).
  • Extractive mock answers: answers quote retrieved sentences verbatim with citations — the mock cannot hallucinate, and it keeps the faithfulness metric in the evaluation honest.
What can go wrong
  • Cache-hit mutation aliasing: on a hit, the code mutates cache_result in place (setting cache_hit/request_id/latency_ms) — and because the memory-tier cache returns the stored dict by reference, those writes persist into the cached entry. It works here because the same fields are overwritten every hit, but adding any conditional mutation would corrupt the cache. The .copy() on the set path is the mirror-image protection.
  • except (ImportError, Exception) in the safe getters is redundant (Exception subsumes ImportError) and dangerously broad: a genuine cache bug (e.g. a corrupted DB) silently turns caching off with no log line. Debugging tip: when cache_hit is永remotely always false, check whether the safe getter is swallowing an exception.
  • Cache staleness on corpus/permission change: keys are (role, query); re-indexing documents or editing allowed_roles leaves stale answers until TTL. Production wants an index-version component in the key.
  • Invalid role returns 200 with an "Access denied" body rather than HTTP 403 — clients can't distinguish auth failure by status code.
Production tradeoffs
  • The _generate_answer seam is where a real LLM (the config already carries DeepSeek settings) slots in — with prompt templating, context-window budgeting, citation-constrained decoding, and streaming responses.
  • Real systems add answer-quality guardrails: groundedness scoring against retrieved chunks, refusal on low retrieval confidence, PII scrubbing of both query and answer.
  • Semantic caching (cache hit on similar queries, not exact strings) multiplies hit rates for natural-language traffic — but must still respect the role dimension.
Interview talking points
  • "The RAG response is observable: grounded flag, citation scores, permission_filtered_count, latency, cache_hit, request_id. When someone asks 'why did the assistant say that', every hop is answerable."
  • "Role-scoped caching is the subtle bit — the cache must be partitioned by every input that affected the answer, and the visible corpus is one of those inputs."
  • "Cache and history are optional dependencies with graceful degradation; retrieval and permissions are not — deciding which failures are survivable is the actual design work."

services/batch_service.py — Async CSV batch scoring

Purpose

Scores whole CSV files of suppliers without blocking the API: start_job() parses and validates the CSV, persists a job row, spawns a daemon thread, and returns a job ID immediately. Clients poll get_job() for status and progress — the classic submit / poll async-job pattern.

Key functions

MemberWhat it does
start_job(data_csv, chunk_size) Parses CSV via csv.DictReader, rejects empty files (ValueError), creates the job row (status pending → running), starts a daemon threading.Thread on _process_job, returns a 16-hex job ID.
_process_job(job_id, records, chunk_size) Iterates in chunks of 10; each record is scored with one retry on failure; failures are recorded as {"supplier_id", "error"} result rows rather than aborting the job. Progress (processed/failed) is persisted after every chunk, so pollers see live progress. Terminal states: completed (with JSON results) or failed (unexpected outer exception).
_map_csv_row(row) / _predict_sync(data) Type-coerces CSV strings with defaults (missing country → "XX" → 0.5 unknown-country risk), then runs the same features → registry → predict/explain path as real-time inference — one model contract, two entry points.
Why chunked + per-record error isolation

A 10,000-row file with one malformed row should produce 9,999 predictions and 1 recorded error — not a dead job. Chunking bounds the granularity of progress updates (one DB write per 10 records, not per record), and per-record try/retry/except converts data-quality problems into inspectable results instead of crashes.

What can go wrong
  • Immediate identical retry: the retry re-runs the same deterministic computation, so a parse error (e.g. non-numeric defect_rate) fails identically twice. Retries pay off for transient faults (network, locks) — with backoff — not deterministic ones. Good self-critique material.
  • Jobs die with the process: daemon threads are killed on shutdown; a restart leaves jobs stuck in running forever with no recovery/reaper logic. Debugging tip: perpetual "running" jobs after a redeploy are exactly this.
  • Results as one JSON blob: the whole result list is serialized into a single results TEXT column — memory-heavy for large jobs and unqueryable. The (unused) batch_job_items table is the schema-ready fix.
  • No concurrency limit: every submitted job gets its own thread; N large uploads = N threads competing with request handling (and the GIL).
Production tradeoffs
  • Replace threads with a real work queue — Celery/RQ/Arq or a cloud-native equivalent (SQS + workers, Cloud Tasks). You gain persistence across restarts, retries with backoff, concurrency control, and dead-letter queues.
  • Large batches stream results to object storage (S3/Parquet) rather than a DB column; the job row stores a pointer.
  • Add idempotency keys so a client-side retry of start_job doesn't double-score.
Interview talking points
  • "Submit/poll with persisted progress is the right API shape; the in-process thread is the demo-scale executor. Swapping the executor for Celery changes zero API surface — that boundary was deliberate."
  • "Batch and real-time share one prediction path (features → registry → model), so a model promotion instantly applies to both — no training/serving-style skew between the two entry points."
  • Be ready for: "What happens if the server restarts mid-job?" — answer honestly (stuck in running) and describe the reaper/queue fix.

services/monitoring_service.py — Platform metrics aggregator

Purpose

Computes the operational dashboard from request_history: latency percentiles (p50/p95/p99 via NumPy), requests-per-minute, error rate, cache-hit rate, per-endpoint breakdowns, an estimated cost figure (per-request unit costs from config), and embeds the drift report from DriftService. One endpoint, one JSON, the whole platform's health.

Key functions

MemberWhat it does
get_metrics() Loads up to 10k history rows; computes np.percentile p50/p95/p99 over latencies; counts rows with timestamps in the last 60 s (defensive ISO parsing, "Z" handling) for RPM; derives error and cache-hit rates; estimates cost as inference_count · $0.002 + rag_count · $0.005; groups rows by endpoint for per-endpoint count / avg latency / error rate; attaches drift_service.get_drift_score().
_empty_metrics() Full-shape zeroed payload when there is no traffic — the dashboard never has to null-check.
Why percentiles and cost, not averages

Averages hide tail pain: one slow dependency turns p99 red long before the mean moves, and users live at the tail. The cost estimate matters because inference cost is a first-class production metric for AI platforms — caching isn't just a latency optimization, it's a budget line, and this endpoint makes that visible (hit rate × unit cost = money saved).

What can go wrong
  • The status-string bug: errors are counted as status != "success", but services log status="ok" — so error_rate reads ~1.0 under healthy traffic. A shared status enum (or counting status not in ("ok","success")) fixes it. Excellent "find the cross-service constant drift" debugging story.
  • Hardcoded rag_citation_rate: 0.85 — a placeholder metric. Never ship a constant pretending to be a measurement; compute it from history payloads or omit it.
  • Percentiles need volume: p99 over 20 requests is just the max; treat small-sample percentiles as noise.
  • Full-table rescan per call: every dashboard refresh re-reads and re-aggregates 10k rows. Cheap now, quadratic pain later.
Production tradeoffs
  • Real systems emit metrics at write time — Prometheus histograms per endpoint, Grafana dashboards, alerting rules on SLO burn rates — instead of recomputing from an audit table on read.
  • RPM from timestamps becomes a proper rate over a rolling window; cost estimation joins actual token/compute billing rather than flat unit prices.
  • Keep this JSON endpoint anyway: a single self-describing health document is gold for demos, smoke tests, and quick triage.
Interview talking points
  • "The four golden signals adapted to ML serving: latency percentiles, traffic, errors, plus the two ML-specific ones — drift and cost. Cache hit rate ties directly to cost per request."
  • "Compute-on-read from an audit log is the simplest correct thing at this scale; I'd move to emit-on-write (Prometheus) the moment traffic makes rescans expensive. Knowing when to make that switch is the senior judgment call."

services/drift_service.py — Usage-drift detection via JSD

Purpose

Detects when the mix of incoming traffic shifts away from expectations. Each historical request is classified into one of five intents; the live distribution is compared to a frozen baseline (40% risk_assessment / 25% compliance / 15% pricing / 12% quality / 8% general) with Jensen–Shannon divergence, and thresholded into ok / warning / alert.

Key functions

MemberWhat it does
_classify_intent(text) Rule cascade over endpoint + query text: inference/"risk" → risk_assessment; RAG queries matched against keyword sets for compliance / pricing / quality; otherwise general. Cheap, deterministic, explainable.
_kld(p, q, eps) / _compute_jsd(p, q) KL divergence with epsilon smoothing (avoids log(0)); JSD unions both key sets, zero-fills, builds the midpoint mixture M = (P+Q)/2, and returns ½KL(P‖M) + ½KL(Q‖M) — symmetric, bounded by ln 2.
get_drift_score() Classifies the last 1000 requests, normalizes to a distribution, computes JSD vs baseline, maps to status via drift_warning=0.20 / drift_alert=0.35, and returns both distributions plus sample size — the report explains itself.
Why JSD, and why intent-level drift

KL divergence is asymmetric (KL(P‖Q) ≠ KL(Q‖P)) and unbounded — a category present in baseline but absent in live traffic sends it to infinity, making thresholds meaningless. JSD fixes both: symmetric, finite, bounded, so "0.20 = warning" is a stable contract. Intent-level drift is the cheapest early-warning layer: it needs no labels and no feature access, just request logs — usage shifting toward compliance queries tells you to re-check RAG coverage before answer quality visibly degrades.

What can go wrong
  • Classifier–baseline coupling: the score measures drift of classified intents. Editing keyword lists silently shifts the measured distribution and can fake (or mask) drift. Version the classifier with the baseline.
  • Frozen hardcoded baseline: if the business legitimately changes (compliance season!), drift alerts forever until someone re-baselines. Production wants baseline as versioned data with a rebaseline workflow, not a class constant.
  • Small-sample noise: JSD over 10 requests swings wildly; gate the status on sample_size before alerting.
  • Substring pitfalls: "risk" in text matches any RAG query containing the word "risk", pulling it into risk_assessment. Keyword classifiers need word-boundary matching.
Production tradeoffs
  • Full drift coverage is layered: usage/intent drift (this), feature drift (PSI/KS per input feature), prediction drift (score distribution shift), and — with labels — performance drift. Tools: Evidently, whylogs/WhyLabs, or warehouse SQL jobs.
  • Intent classification upgrades from keywords to embedding-cluster assignment; drift then compares cluster occupancy.
  • Run drift as a scheduled job with windowed comparisons (this week vs training window), not on-demand over "last 1000 rows".
Interview talking points
  • "I chose JSD over KL deliberately: symmetric and bounded means thresholds are stable even when a category drops to zero — with KL that's a division-by-epsilon explosion."
  • "The report returns both distributions, not just a number — a drift score you can't explain is an alert nobody trusts. Ours shows exactly which intent grew."
  • "Drift detection is a hierarchy of cost vs signal: usage drift is free (logs only), performance drift is gold but needs labels. You build the cheap layers first."

services/evaluation_service.py — Golden-set RAG evaluation

Purpose

Regression testing for the RAG system. It replays a curated set of GOLDEN_QUESTIONS (each with expected doc IDs and expected answer keywords) through the live pipeline and scores four metrics per question — recall@k, precision@k, faithfulness, citation accuracy — then averages them and raises a regression_detected flag when quality drops below thresholds.

Metrics computed

MetricFormulaQuestion it answers
recall_at_k|expected ∩ retrieved| / |expected| Did retrieval find the documents that contain the answer?
precision_at_k|expected ∩ retrieved| / |retrieved| How much of what we retrieved was actually relevant?
faithfulnessfraction of expected keywords present in the answer Does the generated answer contain the right content? (keyword proxy)
citation_accuracy|cited ∩ expected| / |cited| Do the citations point at the right sources?

Questions with recall < 0.5 are collected into failed_cases with expected-vs-retrieved doc IDs — the debugging payload, not just a score. Regression fires when avg recall < 0.6 or avg faithfulness < 0.5.

Why golden-set evaluation

RAG systems degrade silently: re-chunk the corpus, swap the embedding model, tweak rerank weights — no test fails, users just get worse answers. A golden set converts "the RAG feels worse" into a number that can gate a deploy, exactly like a unit-test suite gates a merge. Because it runs through the real service stack (retrieval, permissions, rerank, generation), it catches integration regressions, not just component ones.

What can go wrong
  • Cache contamination: evaluation queries hit the same RAG cache as production traffic — a second evaluation run may score cached answers, and eval queries pollute the cache. Evaluations should bypass or namespace the cache.
  • Keyword faithfulness is a weak proxy: an answer can contain every keyword and still be wrong (or contradictory). It's honest for the extractive mock generator; with a real LLM you need LLM-as-judge or NLI-based groundedness scoring.
  • Golden-set rot: expected_doc_ids break when documents are re-chunked or re-IDed. The golden set is a versioned artifact that must migrate with the corpus.
  • Role-dependence: results are computed as role="analyst"; a permission change can move scores without any retrieval change. That's a feature (it catches permission regressions) but a confusing one if you don't know it.
Production tradeoffs
  • Wire into CI/CD: run on every PR touching retrieval/prompt/index code, block merge on regression — the ML analog of a test suite. Frameworks: Ragas, TruLens, DeepEval, or this exact hand-rolled shape.
  • Store evaluation runs over time (per model/index/prompt version) to draw quality trendlines, not just point-in-time pass/fail.
  • Grow the set from production: mine low-confidence or thumbs-down queries into new golden questions.
Interview talking points
  • "Retrieval and generation need separate metrics — recall@k tells you if search failed, faithfulness tells you if generation failed. One blended score can't tell you which stage to fix."
  • "failed_cases with expected-vs-retrieved doc IDs is the difference between an alarm and a diagnosis."
  • "The regression flag exists to gate deploys — evaluation that doesn't block anything is a dashboard, not a control."

ml/supplier_risk_model.py — Risk models behind one contract

Purpose

Defines the model contract and two implementations. BaseRiskModel (ABC) requires predict(features) → {risk_score, risk_level} and explain(features) → list[factor contributions] — note that explainability is part of the interface, not an afterthought.

Key pieces

MemberWhat it does
RuleBasedModel.predict() Weighted sum over five normalized features — defect_rate 0.30, late_delivery 0.25, country_risk 0.20, lead_time 0.15, order_value 0.10 — clamped to [0,1], then bucketed by thresholds (≥0.85 critical, ≥0.70 high, ≥0.40 medium, else low).
RuleBasedModel.explain() Exact additive attribution: each factor's impact is literally value × weight, tagged with a direction, sorted by impact. Because the model is linear, the explanation is provably faithful — it sums to the score.
TrainedModel Loads a pickled sklearn classifier if the artifact path exists; otherwise is_using_fallback=True and all calls delegate to an internal RuleBasedModel. Predicts via predict_proba(...).max(); explains via feature_importances_. Features are ordered by sorted key names (excluding supplier_id) to build the vector.
Why start rule-based

Day one, there is no labeled training data. A weighted scorer encodes domain knowledge, ships immediately, is 100% explainable, and — crucially — establishes the serving contract that a trained model must later satisfy. It then becomes the permanent safety net: the trained model can fail to load, the rule-based one cannot.

What can go wrong
  • Silent fallback: a missing/renamed artifact path quietly serves rule-based scores while everyone believes the trained model is live. is_using_fallback exists but nothing logs or exposes it — surface it in /health and metrics.
  • Feature-order skew: sorted-key ordering must match training exactly; adding one feature to build_features shifts every vector position and silently corrupts trained-model predictions. Production stores an explicit feature list with the artifact.
  • predict_proba(...).max() is not a risk score: it's the confidence of the most likely class — for a confident "low-risk" prediction it returns a high number that then thresholds as "critical". It should be the probability of the positive/high-risk class.
  • Pickle is unsafe: loading a pickle executes arbitrary code (the # noqa: S301 acknowledges it). Production wants signed artifacts, ONNX, or joblib from a trusted registry only.
  • feature_importances_ are global, not per-prediction — every request gets the same "explanation". Honest per-prediction attribution needs SHAP/TreeExplainer.
Production tradeoffs
  • Rule-based → gradient-boosted trees (XGBoost/LightGBM) with SHAP explanations; calibrate probabilities (Platt/isotonic) so thresholds mean what they say.
  • Champion/challenger: keep the rules as a sanity baseline; alert when trained-model outputs diverge wildly from the rule score for the same input.
  • Artifact management moves to MLflow/SageMaker registry with lineage: data version, training code commit, metrics, approval status.
Interview talking points
  • "Explainability is in the ABC — you cannot register a model here that can't explain itself. For supplier risk (a decision with money on the line), that's a requirement, not a nice-to-have."
  • "The rule model's explanation is provably faithful because the model is additive. The moment we go to trees, faithful attribution costs SHAP compute — that's a real tradeoff to name."
  • Call out the predict_proba().max() bug yourself if asked to critique the code — it's the exact kind of subtle ML-serving bug interviewers love.

ml/feature_builder.py — Deterministic feature engineering

Purpose

The single transformation from a raw supplier record to the normalized feature dict every model consumes. Both real-time inference and batch scoring call this exact function — one implementation, zero training/serving-skew risk between entry points.

Key functions

FunctionWhat it does
normalize_* (lead_time, defect_rate, late_delivery, order_value) Divide by a domain cap (120 days, 25% defects, 50 late deliveries, $500k) and clamp to [0,1] — min-max scaling with fixed, documented bounds instead of data-dependent statistics.
get_country_risk(country) Lookup in a 10-country risk table (e.g. DE 0.10 … BD 0.50); unknown country → 0.5 — "we don't know" is deliberately scored as medium risk, not zero risk.
build_features(supplier_data) Assembles the five normalized features plus two engineered ones: defect_cost_interaction (defect_rate × order_value / cap — a 5% defect rate hurts far more on a $400k order) and delivery_reliability (1 − late/cap, an inverted "good" framing). Everything rounded to 6 decimals for stable cache keys and logs.
Why fixed caps instead of fitted scalers

A fitted StandardScaler is state that must be versioned, shipped with the model, and kept in sync — the #1 source of training/serving skew. Fixed domain caps are stateless, interpretable ("120 days is the worst lead time we consider"), and identical everywhere by construction. The cost: they're opinions, and outliers saturate at 1.0.

What can go wrong
  • KeyError on missing fields: build_features indexes raw fields directly (supplier_data["lead_time_days"]). The API path is safe (Pydantic validated) — but any new caller passing a partial dict crashes. Batch protects itself with _map_csv_row defaults.
  • Saturation hides magnitude: 130 and 400 lead-time days both normalize to 1.0. If tails matter, add log-scaling or an "exceeds cap" flag feature.
  • Interaction uses raw defect_rate: defect_cost_interaction multiplies the raw rate (0–0.25 typical) by normalized order value, so the interaction lives in a much smaller numeric range than the other features — a trained model handles that, but the rule-model weights ignore this feature entirely (it's not in _WEIGHTS).
  • Country table maintenance: a hardcoded geo-risk map is a governance artifact pretending to be code — it needs an owner, sourcing, and review cadence in production.
Production tradeoffs
  • At scale this becomes a feature store (Feast, Tecton): batch-computed aggregates (rolling 90-day defect rate) served online with guaranteed training/serving consistency and point-in-time correctness.
  • Feature definitions get versioned; a model artifact pins the feature-set version it was trained on.
  • Add input-validation telemetry: distribution of each raw field, rate of cap saturation, unknown-country rate — these are your feature-drift sensors.
Interview talking points
  • "One feature function shared by online and batch paths is my skew story: there is no second implementation to drift."
  • "Unknown country defaults to 0.5, not 0 — missing data as 'medium risk' is a domain decision encoded in code, and I can point at the line."
  • "Interaction features are where domain knowledge enters: defect_rate × order_value expresses that quality problems scale with financial exposure — a linear model can't learn that on its own."

ml/model_registry.py — Model versioning and stage management

Purpose

An in-memory registry mapping versions to ModelVersion records (name, semver, stage, live model instance, registration timestamp). Stages are a typed Literal["production", "canary", "archived"] — the standard promotion lifecycle. On construction it bootstraps supplier-risk-rule-based v1.0.0 into production so the platform always has a servable model.

Key functions

MemberWhat it does
register(name, version, stage, model_instance) Creates and stores a ModelVersion keyed by version string; returns the entry.
get_production() Linear scan for the first version staged "production" — the lookup inference and batch make on every prediction, which is what makes promotion instant.
get_by_version(v) / list_versions() Direct lookup (pinned scoring, A/B) / enumeration for a models API.
Why indirection between callers and models

No service ever constructs a model — they ask the registry for "current production". That single indirection is what makes deploy-time model swaps, canaries, and rollbacks possible without code changes: promotion is a registry state change, not a redeploy. The bootstrap default encodes "the platform must never have zero servable models".

What can go wrong
  • Nothing prevents two "production" versions — register() doesn't demote the incumbent, and get_production() returns whichever iterates first (dict insertion order). Promotion must be atomic: promote-new + demote-old in one operation.
  • Keying by version only: two different model names with the same version string collide and overwrite. Key should be (name, version).
  • Multiple registry instances: InferenceService and BatchService each construct their own ModelRegistry(). They agree today only because bootstrap is deterministic — register a canary in one and the other never sees it. The registry should be a shared singleton (or external service).
  • In-memory = amnesia: restart loses all registrations except bootstrap; there's no audit trail of who promoted what when.
Production tradeoffs
  • This is the interface of MLflow Model Registry / SageMaker Model Registry: persistent versions, stage transitions with approval workflows, lineage to training runs, artifact storage.
  • Canary stage becomes real traffic splitting (5% → compare metrics → promote/rollback), driven by the registry's stage field.
  • Registry state changes should emit events — cache invalidation (the stale-prediction issue from inference_service) hangs off "model promoted".
Interview talking points
  • "Model registry is the control plane of MLOps: deployment = stage transition, rollback = stage transition. My version is in-memory, but every caller already speaks the registry protocol, so swapping in MLflow touches one class."
  • "I typed stages as a Literal so an invalid stage is a type error, not a runtime surprise."
  • Discuss the dual-instance flaw proactively — spotting shared-state bugs across service boundaries is a senior signal.

storage/vector_store.py — In-memory vector search

Purpose

A minimal vector database: parallel structures of document dicts and an np.ndarray embedding matrix, with thread-safe add/search/clear. Search is exact (brute-force) cosine similarity — with the crucial twist that the permission filter runs before any similarity math.

Key functions

MemberWhat it does
add_documents(docs, embeddings) Appends docs; vstacks embeddings onto the existing matrix (or sets it). Lock-guarded so concurrent adds can't interleave docs and rows out of sync.
search(query_embedding, top_k, filter_fn) 1) Build the candidate list, skipping any doc rejected by filter_fn (permission pre-filter). 2) Slice the embedding matrix to candidate rows. 3) Normalize query and candidates (with +1e-10 epsilon against zero vectors), compute cosine similarities in one matrix-vector product. 4) np.argsort(...)[::-1][:top_k], return docs with float scores and metadata.
clear()Resets both structures — used by tests and reseeding.
Why brute-force, and why filter-then-rank

Exact search over a few hundred docs is a single NumPy matmul — microseconds, with perfect recall. ANN indexes (HNSW/IVF) only earn their complexity around 10⁵–10⁶ vectors. Filtering before ranking serves the security invariant (unauthorized docs never scored) and also mirrors a hard real-world problem: filtered ANN search is genuinely difficult (filters break graph connectivity in HNSW), which is why vector DBs advertise pre-filtering support as a feature.

What can go wrong
  • Docs/embeddings desync: add_documents accepts docs with embeddings=None (the seeding path does this; EmbeddingService fills the matrix later). Between those moments, index positions must stay aligned — any code that adds docs after embedding bootstrap breaks the parallel-array invariant and returns wrong documents for right scores. Nastiest possible bug class: no exception, just subtly wrong results.
  • Unlocked emptiness check: the if not self.documents or self.embeddings is None guard runs before acquiring the lock — a benign race here, but a reminder that check-then-act needs the lock in general.
  • Full argsort: O(n log n) over all candidates when top-k needs only np.argpartition O(n). Irrelevant at this size; the first profiler finding at scale.
  • No persistence: restart → empty store until reseed + re-embed. Fine because seeding is in the lifespan hook; surprising if you forget that.
Production tradeoffs
  • Path of least resistance: pgvector — vectors live next to relational data, permission filters become WHERE clauses, one database to operate. Dedicated engines (Qdrant, Weaviate, Milvus, Pinecone) when scale/latency demand ANN + sharding.
  • ANN introduces a recall/latency dial (HNSW ef_search) — retrieval quality becomes a tunable, which is exactly why the golden-set evaluation exists.
  • Store doc + chunk + embedding-model-version together; the version mismatch problem from embedding_service is solved at the schema level.
Interview talking points
  • "Brute-force cosine is the right call under ~100k vectors — perfect recall, one matmul, no index ops. Knowing when not to use a vector database is the senior answer."
  • "Pre-filtered search is the hard part of real vector DBs — filters break HNSW graph traversal. My linear-scan store gets it trivially; that's the tradeoff conversation."
  • "The parallel-array invariant (docs[i] ↔ embeddings[i]) is the store's core fragility — in production the pairing is a single row/point, never two structures."

storage/database.py — SQLite schema and connections

Purpose

Owns the entire relational schema (idempotent CREATE TABLE IF NOT EXISTS script) and connection construction. Four tables: request_history (audit log), batch_jobs (job lifecycle + results blob), batch_job_items (per-item results — schema-ready, not yet used by the service), and cache_entries (persistent cache tier with TTL).

Key functions

FunctionWhat it does
init_db() Creates the data directory (mkdir(parents=True, exist_ok=True)) and runs the schema script. Idempotent — safe on every startup; called from the FastAPI lifespan hook.
get_connection() New connection per call with three deliberate settings: row_factory = sqlite3.Row (dict-like rows → dict(row) in repositories), PRAGMA journal_mode=WAL (readers don't block the writer — essential since batch threads write while API requests read), and PRAGMA foreign_keys=ON (off by default in SQLite!).
Why SQLite, and why WAL

Zero-ops, single-file, transactional, and honestly sufficient for a demo platform's write volume. WAL mode is the non-obvious expert choice: default rollback-journal mode lets a single writer block all readers; WAL gives concurrent readers + one writer, which this app genuinely needs (background batch thread writing progress while monitoring reads history).

What can go wrong
  • "database is locked": WAL still allows only one writer; concurrent writers (batch progress + history inserts) can collide. No busy_timeout is set, so a collision raises immediately instead of waiting. First fix: PRAGMA busy_timeout=5000.
  • Connection-per-operation overhead: every repository method opens/closes a connection — correct and leak-proof, but each open re-runs PRAGMAs. A pool (or thread-local connections) is the next step.
  • No migration story: IF NOT EXISTS creates but never alters — adding a column to an existing deployment silently does nothing. Real evolution needs Alembic-style versioned migrations.
  • No indexes: request_history is queried by endpoint and ordered by timestamp with no index on either — table scans that grow with the audit log.
  • Timestamps: CURRENT_TIMESTAMP is UTC but stored without timezone info; note the careful replace(tzinfo=timezone.utc) dance in CacheRepository — mixing naive and aware datetimes is a classic TTL bug source.
Production tradeoffs
  • Postgres for multi-writer concurrency, real types (JSONB, TIMESTAMPTZ), and — with pgvector — the vector store merges into the same database.
  • Repositories keep raw SQL isolated, so the migration is mechanical: swap the connection factory, parameter style, and upsert syntax. That containment was the design goal.
  • Introduce connection pooling (or SQLAlchemy engine) and versioned migrations before any schema change ships.
Interview talking points
  • "Two PRAGMAs show I know SQLite's sharp edges: WAL for reader/writer concurrency, and foreign_keys=ON because SQLite ships with FK enforcement disabled."
  • "SQLite-to-Postgres is a swap of the connection factory precisely because no SQL leaks above the repository layer."

storage/repositories.py — Data-access layer

Purpose

All SQL in the codebase lives here, in three repositories mapping 1:1 to concerns: history, batch jobs, cache. Services speak dicts; repositories speak SQL. Every method is parameterized (no string-built SQL) and uses try/finally conn.close() so connections never leak, even on error.

Key methods

RepositoryHighlights
HistoryRepository insert() with named parameters, JSON-encoding the payload dict; query() newest-first with optional endpoint filter and limit; count().
BatchJobRepository Job lifecycle: create() (status "pending", returns the created row), update_progress() (processed/failed counts), update_status() — which stamps completed_at automatically when status enters a terminal state ("completed"/"failed"), get(), list_all().
CacheRepository get() enforces TTL: computes elapsed seconds since created_at (re-attaching UTC tzinfo) and lazily deletes + returns None when expired. set() is an atomic upsert via INSERT ... ON CONFLICT(cache_key) DO UPDATE, resetting created_at so TTL restarts on overwrite. clear_expired() bulk-deletes using julianday() arithmetic entirely in SQL.
Why the repository pattern (and lazy TTL)

Services stay testable (fake a repo, no DB) and the SQLite→Postgres migration is contained to this file. Lazy expiration — checking TTL on read instead of running a background sweeper — is exactly how Redis handles expiry for most keys: no timer machinery, expired entries cost nothing until touched, and clear_expired() exists for occasional bulk cleanup.

What can go wrong
  • update_status(job_id, "running") nulls results: update_status always writes the results column — passing no results on an intermediate transition sets it to NULL. Harmless in the current call order (results only exist at completion), but a trap for the next caller. Partial-update SQL should only touch provided columns.
  • Naive-vs-aware datetime handling in CacheRepository.get(): created_at parses as naive and gets UTC re-attached manually. It works because SQLite's CURRENT_TIMESTAMP is UTC — but that assumption is one column default away from a subtle TTL bug (entries expiring 7 hours early/late depending on server timezone).
  • Two TTL implementations must agree: get() uses Python datetime math; clear_expired() uses SQL julianday math. If their semantics ever diverge, reads and sweeps disagree about what's expired.
  • No transactions across calls: each method commits independently; a multi-step operation (e.g. create job + first progress update) is not atomic. Fine for current usage; a unit-of-work pattern if it grows.
Production tradeoffs
  • Hand-rolled repos vs ORM: raw SQL keeps the demo transparent and dependency-light; SQLAlchemy Core is the sweet spot at team scale (typed, composable, still explicit).
  • The upsert-with-timestamp-reset in CacheRepository.set() maps 1:1 to Redis SETEX — the migration is method-for-method.
  • Batch results move from a TEXT blob to the batch_job_items table (already in the schema) or object storage, enabling per-item queries and streaming reads.
Interview talking points
  • "Every query is parameterized and every connection is closed in a finally block — boring by design; data layers should be boring."
  • "Lazy TTL on read plus an explicit sweeper is the same strategy Redis uses — I can explain why that beats a background timer at this scale."
  • "The repository boundary is my database-migration insurance: services have never seen a SQL string."
